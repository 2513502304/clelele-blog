# 2026-09-20：十张原文件与 JSONL 导入源字节核验

## 网站最终保存哪张图

这次核验要回答的是：本地附件已经丢失，只剩 Codex 会话文件时，导入到网站的图片还能否保持原样。模型为了识图而缩小输入，是另一个问题。两者需要分开，因为同一条消息在 JSONL 中可能保存两份不同大小的图片。

用户新建了会话 `01a0be42-312e-7f41-b475-9c1a3ef26de4`，并按发送顺序提供全部十张原文件。前五张由 VS Code Codex 扩展发送；第六张在 Codex App 中立即发送，第七至十张排队发送。这个顺序和界面中的附件图标由用户记录。

VS Code 的五张图片都以原始字节保存在 UI 消息中，现有导入器会选择这份数据。因此，即使附件不存在，五张图仍能原样上传。第 3–5 张是超大图片，模型输入虽然被缩小，UI 消息里的原图却没有变化。现在有磁盘原文件作对照，可以明确说这五张保存了原图；先前报告缺少原文件，只能确认它们比模型输入大。

App 的结果不同。第六张立即发送的大图没有显示附件图标，JSONL 中却只内嵌了缩小后的图片；另外保存的本地路径必须指向仍然存在的文件，才能恢复原图。第 7、9、10 张排队消息也保存了缩小版，第 8 张则与原文件一致。这说明立即发送和排队发送都可能发生处理，附件图标不能告诉用户图片是否已经压缩。

这些结论针对本次实际使用的输入路径。对于“尽量不依赖本地附件，仍能从 JSONL 收藏原图”这个需求，本次 VS Code 的表现符合要求。更换客户端版本、输入方式或设置后，需要重新核对，不能把这次结果当作永久保证。

## 怎样验证

核验脚本逐行读取整份 JSONL，找到十条完整的图片与 Prompt 配对。每条都比较三份数据：用户提供的磁盘原文件、UI 消息中的内嵌图片、模型输入中的图片。比较使用完整 SHA-256 和逐字节相等检查，不以肉眼相似或尺寸相同代替文件一致。

随后直接调用导入脚本的 `readSessionItems`，读取它实际选中的图片，但不调用恢复本地附件的步骤。这样就能回答“附件全部丢失”的问题，而不受附件是否仍在电脑上的影响。下表记录的是导入器选中的源图片字节。这十张对照样本没有执行上传、网络写入或图片替换，表格不是线上卡片的回读结果。按当前导入逻辑，新卡片使用选中的源字节，另行生成缩略图；已发布的卡片仍遵循默认保留、显式 `--overwrite-images` 才替换的规则。

## 附件与行号

前五张没有文件说明、图片路径包装或结构化本地附件字段，原始字节直接保存在 UI 图片中。第六张的 UI `images` 为空，有图片路径包装和一个 `user_message.local_images`；后四张有文件说明，图片字节保存在 UI `images` 中。

导入器支持 `user_message.local_images` 和 `item_completed.UserMessage.local_image` 两种结构化附件记录，也支持只有完整文件说明和内嵌图片的 Desktop 消息。后一种情况要求模型与 UI 记录中的文件名、绝对路径及图片数量逐项对应，且属于同一输入；不要求存在 `<image path>` 包装。UI 与模型图片可能尺寸不同，读取附件后会分别校验内容。UI 消息保存了更大的内嵌图片时，脚本保留这份图片，同时保留已经确认的附件关联。普通 Prompt 里提到的文件路径不会被当作原附件读取。

## 对旧结论的修正

1. 先前九张样本缺少 VS Code 的磁盘原图，所以“无法证明逐字节一致”是那组样本的证据限制，不是 VS Code 未保留原图的证据。此次新样本补齐了对照，五张全部一致，包含三张超大原图。
2. 不应把“VS Code 的模型投影经过缩放”拿来回答“导入网站的图是否原始”的问题。必须检查导入器实际选中的 UI 字节。
3. 第六张推翻“没有图标就没有处理”；第八张推翻“有图标就已经处理”。图标不是压缩开关指示。
4. 不能继续把此前重复 hash 问题简单归因为“新版才压缩、旧版不压缩”。当前证据确认输入客户端/路径的存储结果不同，尚未隔离出版本、开关和输入方式各自的因果作用。
5. 会话第 1、64 行的 `session_meta` 都仍是 `codex_vscode / 0.154.0-alpha.6.2 / source=vscode`。同一会话后续转到 App 时元信息没有可靠区分每条消息的客户端，不能把会话级 originator 当成每条输入的证明。

维护时应保留 UI 图片优先的提取行为；对已确认的结构化附件再执行恢复与校验。没有可恢复原始字节时，不能逆向还原已经有损缩小的原文件，也不能仅凭视觉相似自动合并不同图片身份。
