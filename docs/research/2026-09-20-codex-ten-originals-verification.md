# 十张原文件与实际导入图片的字节核验

核验于 2026-09-20；结论整理于 2026-09-23。要回答的问题是：**本地附件全部丢失，只剩 JSONL 时，网站收藏的是否还是原图？** 模型为了识图缩小输入，与网站最终保存哪份图片，需要分开判断。

## 结论

本次 VS Code Codex 扩展发送的五张图片，均以原始字节保存在 UI 记录里，包括三张超大图。调用导入器、禁用附件恢复后，选中的图片仍与磁盘原文件逐字节一致。对于这组输入，即使附件丢失也能收藏原图。

Codex App 的五张图片中，四张内嵌图已缩小，一张仍与原文件一致。第六张是立即发送的大图，没有附件图标，但已经缩小；第八张有图标，字节却没有变化。因此，立即发送和排队发送都可能处理图片，附件图标不能用来判断压缩。

这支持用户优先采用本次 VS Code 输入路径来保留 JSONL 原图，但不能保证所有版本、设置和粘贴方式都如此。会话跨客户端续接时，`source`、`originator` 和记录版本也未必随每条消息改变，不能只凭会话头部判断输入客户端。

## 样本与方法

用户提供会话 `01a0be42-312e-7f41-b475-9c1a3ef26de4` 的全部十张磁盘原文件。前五张来自 VS Code；第六张由 App 立即发送，第七至十张排队发送。客户端、发送方式及图标状态由用户记录。

逐行配对图片与回复，比较磁盘原图、UI 内嵌图、模型输入投影的完整 SHA-256 和实际字节。另调用 `readSessionItems`，不运行本地附件恢复，验证导入器真正选择的源图。这是本地读取实验，表中数字不是生产上传统计。

## 已排除的猜想

下表保留曾经看似合理、但已被样本推翻的判断，避免后续维护重复走弯路。它们不是当前结论；右栏的证据范围也不应扩大到所有客户端版本。

| 曾经的猜想 | 为什么不能成立 | 后续应怎样判断 |
| --- | --- | --- |
| 没有附件图标，就没有压缩；有图标，就压缩过 | 第六张无图标却缩小，第八张有图标却逐字节未变 | 比较原文件与 JSONL 实际图片，不能用图标替代字节核验 |
| App 只处理排队图片，立即发送会保留原图 | 第六张是 App 队列的第一条、立即发送的大图，仍然缩小 | 发送时机不是是否缩放的充分判断依据 |
| 模型输入缩小了，网站导入的也一定是缩小图 | VS Code 的第三至五张模型投影缩小，但 UI 图和实际导入结果仍与原文件一致 | 分别检查 UI 图、模型图与导入器选中的图 |
| 没有本地附件字段，JSONL 就不能保存原图 | 前五张没有附件字段，UI 内嵌图仍逐字节保留原文件 | 附件路径和内嵌原图是不同的保存方式 |
| JPEG 即使满足预算，也一定会重新压成 quality 85 | 第八张为预算内 JPEG，字节完全未变；已核对源码也有原字节直通分支 | 区分是否进入重编码分支，不能只看文件格式 |
| 最大边不超过 2048，就不会缩放 | `1289×2048` 仍占 2624 个图块，超过 High 的 2500 图块预算 | 同时检查最长边和图块数，且先确定适用的 detail 预算 |

另有两项只能说“尚未证明”，不能写成已证实或已证伪：一是“所有 VS Code 输入路径永远保留原字节”，二是“差异完全由 App 的某个默认开关造成，与版本无关”。本次对照证明了这十张图的存储差异，但没有覆盖全部版本、设置和剪贴板路径。更早的源码已经存在缩放逻辑，也不足以反推出某个客户端何时启用了它。

## 对维护的要求

前五张没有本地附件字段，原图直接保存在 UI 图片中。第六张的 UI `images` 为空，但有 `user_message.local_images`；后四张带文件说明和 UI 内嵌图片。附件信息的不同形式应按同一输入关联，不能以是否存在某一个字段代替内容验证。

导入器优先保留可用的 UI 图片，再对已确认归属的本地附件进行内容校验和恢复。附件全部丢失时只能使用 JSONL 实际保留的字节；已经有损缩小的图片无法凭空还原。源图与缩略图分别保存；已有卡片默认保留图片，显式 `--overwrite-images` 才检查替换。

三种图片的定义、编码和去重规则见[图片来源与压缩说明](2026-09-19-codex-image-preprocessing.md)，实现约束见[存储文档](../style-gallery-storage.md)。
