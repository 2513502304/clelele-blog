# 2026-09-20：十张原文件与 JSONL 实际导入字节核验

## 结论：这里只讨论收藏到网站的图片

用户新建会话 `01a0be42-312e-7f41-b475-9c1a3ef26de4`，按发送顺序提供了十张磁盘原文件。前五张使用 VS Code Codex 扩展，第六张使用 Codex App 立即发送，第七至十张在 App 中排队。客户端分组、立即/排队和 UI 附件图标状态来自用户操作记录。

**本次 VS Code 五张全部保留原始字节；在附件全部丢失的条件下，现有导入脚本仍会选中这五张原图。** 第 3–5 张本来超过尺寸预算，模型投影被缩小，但 `event_msg:user_message.images` 保留完整原文件。这是模型输入优化，不影响导入器收藏的原图，不能据此反驳“VS Code 为收藏保留原图”。

**App 第六张立即发送的大图已被缩小；没有附件图标也不代表未处理。** 它的 UI `images` 为空，JSONL 保存了 `local_images` 路径和图片路径包装，但路径不是内嵌原始字节。附件丢失时，脚本只能选中缩小后的模型投影。第 7、9、10 张排队消息的 UI 图片也已缩小；第 8 张未超限，原文件、UI、模型和导入字节一致。

这组对照支持用户猜想 1 对当前收藏路径的判断，否定“仅 App 排队图片才会处理”的猜想 2。更准确的工程结论是：本次 VS Code 输入路径保留原图供导入，App 的立即和排队路径都可能只内嵌处理后的图；不能扩大为所有版本、格式、粘贴方式或设置的永久保证。

## 方法与范围

- 流式读取整份 JSONL，确认十条带图片输入和十条有效图片/Prompt 配对。
- 按用户指定顺序比较磁盘原文件、UI 内嵌数据和 `response_item:input_image`，计算完整 SHA-256，并以 `Buffer.equals` 实际验证逐字节一致性；不是仅比较尺寸、短 hash 或视觉相似度。
- 直接调用当前 `scripts/import-style-prompts.mjs` 导出的 `readSessionItems`，检查其选中图片；不调用 `resolveOriginalImages`，模拟所有附件不可用。未执行导入入口、任何网络写入或图片替换。
- 下表讨论新卡片的 source 资产字节；已发布卡片默认仍保留线上图片。脚本单独生成缩略图，不把选中的 source 再压缩。
- 仅本地只读核验和文档/注释修正；没有修改解析或上传逻辑。

## 对旧结论的修正

1. 先前九张样本缺少 VS Code 的磁盘原图，所以“无法证明逐字节一致”是那组样本的证据限制，不是 VS Code 未保留原图的证据。此次新样本补齐了对照，五张全部一致，包含三张超大原图。
2. 不应把“VS Code 的模型投影经过缩放”拿来回答“导入网站的图是否原始”的问题。必须检查导入器实际选中的 UI 字节。
3. 第六张推翻“没有图标就没有处理”；第八张推翻“有图标就已经处理”。图标不是压缩开关指示。
4. 不能继续把此前重复 hash 问题简单归因为“新版才压缩、旧版不压缩”。当前证据确认输入客户端/路径的存储结果不同，尚未隔离出版本、开关和输入方式各自的因果作用。
5. 会话第 1、64 行的 `session_meta` 都仍是 `codex_vscode / 0.154.0-alpha.6.2 / source=vscode`。同一会话后续转到 App 时元信息没有可靠区分每条消息的客户端，不能把会话级 originator 当成每条输入的证明。

维护时应保留 UI 图片优先的提取行为；对已确认的结构化附件再执行恢复与校验。没有可恢复原始字节时，不能逆向还原已经有损缩小的原文件，也不能仅凭视觉相似自动合并不同图片身份。
