## 为什么并非每张 JPEG 都 quality 85

[会话记录版本 0.154.0-alpha.6.2 的图片库](https://github.com/openai/codex/blob/rust-v0.154.0-alpha.6.2/codex-rs/utils/image/src/lib.rs) 和 [0.155.1 实现](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/utils/image/src/lib.rs) 的 `load_for_prompt_bytes_uncached` 在需要缩放时才调用重编码；支持的格式不需要改变尺寸时直接保留 `file_bytes`。`JpegEncoder::new_with_quality(..., 85)` 是重编码分支，不是无条件执行。

本会话多个 `session_meta` 仍标记 `codex_vscode` / `0.154.0-alpha.6.2`；用户更新独立 CLI 为 0.155.1 不能证明扩展或 Desktop 使用同一二进制。恢复旧会话的元信息也不能准确标识每条后续消息的客户端，故这里客户端分组以用户提供的操作顺序为依据。

缩小分辨率会丢失细节，JPEG 重编码也有损；文件变大并不能说明无损，例如第 4 张模型图更小但字节反而多于 UI 图。第 5、9 张则逐字节未变。

## 对导入和去重的影响

导入器当前可使用较大的 UI 图片；有受验证的同回合结构化原附件时优先恢复。不要为了符合模型预算而改成一律导入 `response_item`，否则会降低收藏质量并改变既有 hash。文件说明中的普通路径文本不单独构成可信附件关联，也不能为恢复更多图片而跳过现有验证。

既有去重仍是原始字节 hash、完全相同的解码像素，以及经过确认的版本关联。UI/模型/磁盘三份图可能有不同 hash；未知的有损版本不能通过“看着一样”自动合并，避免误合并。

## 附件全部丢失时，导入器到底上传什么

导入脚本优先采用可用的 `event_msg:user_message.images`；如果该记录没有内嵌图片，则保留前面的 `response_item:input_image`。脚本生成独立缩略图，不改写所选 source 图片字节。对已经发布的卡片，默认导入保留线上图片，只追加不同 Prompt；下表讨论新图片在无附件情况下的来源。

| 入口（本组样本） | 无附件时导入的图片 | 能否确认原图 |
| --- | --- | --- |
| VS Code，1–4 | UI 记录，687×431 / 2498×4096 / 2508×3541 / 1451×2048 | 保留比模型投影更大的输入；缺少磁盘原文件，不能对这四张宣称已做原图字节校验 |
| Desktop 立即，5 | 模型投影，1231×2048 | 与磁盘原文件逐字节相同 |
| Desktop 排队，6–8 | UI 记录，1054×2048 / 2048×2048 / 1451×2048 | 已经缩放，均不同于磁盘原文件 |
| Desktop 排队，9 | UI 记录，1216×832 | 与磁盘原文件逐字节相同 |

因此，在本次观察的输入路径下，VS Code 的 JSONL 更有利于保留大图；Desktop 无附件 fallback 可能只能恢复已经缩小的输入。客户端不是跨版本/所有输入方式的质量保证，图标也不能作判断依据。
