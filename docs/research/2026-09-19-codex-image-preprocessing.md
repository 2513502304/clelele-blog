# Codex 图片来源、压缩与 Gallery 去重

本页汇总 2026-09-19 至 09-20 的核验，2026-09-23 整理。判断收藏质量时，先看导入器实际选择的图片，再比较原文件；不要把模型输入缩放、附件图标或客户端名称当作原图质量的证明。

## JSONL 中可能有哪几份图片

| 名称 | 含义 | 与收藏质量的关系 |
| --- | --- | --- |
| 磁盘原附件 | 用户上传前的本地文件，JSONL 可能只记录路径 | 文件仍存在、关联和内容校验通过时，可以恢复原始字节 |
| UI 图片 | 用户消息里保存的内嵌图片，常见于 `event_msg:user_message.images` | 可能保留原图，也可能已被客户端缩小；脚本优先使用可用的这份数据 |
| 模型输入投影 | `response_item:input_image` 等送入模型的图片 | 可能为满足模型预算再次缩小，不能据此判断 UI 图或网站源图也变小了 |

本地附件不可用时，脚本仍能读取内嵌图，但无法恢复内嵌前已丢失的细节。脚本不会重新压缩选中的源图，只会另外生成缩略图。具体来源和默认保留／显式覆盖规则见[存储文档](../style-gallery-storage.md)。

## VS Code 与 App 的实测区别

[十张原文件的直接对照](2026-09-20-codex-ten-originals-verification.md)中，VS Code 的五张 UI 图片全部与磁盘原文件一致，包括三张超大图；模型投影中的缩放不影响导入器从 UI 记录读取原图。App 的五张中四张已缩小，一张未变。

App 立即发送的大图也发生了缩小，尽管 UI 没显示附件图标；另一张显示图标的图片则逐字节未变。**图标不能判断压缩，排队也不是缩放的必要条件。** 这些样本能证明本次输入路径的差异，不能证明某客户端永远不处理图片，或某个版本、开关是唯一原因。

曾经关于附件图标、排队时机和模型输入的猜想及其反证，集中保留在[已排除的猜想](2026-09-20-codex-ten-originals-verification.md#已排除的猜想)，正文不再沿用这些旧判断。

## 尺寸预算与编码

核对的 [0.154.0-alpha.6.2 图片实现](https://github.com/openai/codex/blob/rust-v0.154.0-alpha.6.2/codex-rs/utils/image/src/lib.rs)中，High detail 同时限制最大边 2048 和最多 2500 个 32×32 图块；Original detail 使用另一组预算。符合尺寸限制且格式支持时可直接保留原始字节；需要缩放时才进入 Triangle 重采样与重新编码分支。JPEG 重编码质量为 85，WebP 重编码采用无损 WebP。这不是“所有 JPEG 每次都压成 quality 85”。

例如 `1289×2048` 的最大边虽合格，但 `ceil(1289/32) × ceil(2048/32) = 2624`，超过 2500，因此仍可能缩为 `1248×1982`。对应实测文件从 384,598 字节变为 504,433 字节，说明缩小尺寸不保证缩小文件。

缩放会丢失细节，JPEG 重编码也有损。若原 WebP 使用有损编码，解码并缩小后再用无损 WebP 保存，最后一步不会再改变像素值，却无法补回此前损失的细节；无损编码也可能比原来的有损编码占用更多空间。历史配对样本中，`3156×2160 / 231,566` 字节变为 `1916×1312 / 2,039,192` 字节。文件更大不表示画质恢复，也不能单凭体积反推原文件采用了哪种编码。

[统一图片准备逻辑](https://github.com/openai/codex/blob/rust-v0.154.0-alpha.6.2/codex-rs/core/src/image_preparation.rs)受 preparation mode、模型能力和特性条件影响。[2026-06-11 的 PR #27247](https://github.com/openai/codex/pull/27247)已经涉及集中缩放；不能把 9 月发现的客户端存储差异简单归因为“9 月新版才开始压缩”。源码和尺寸对照说明机制相符，并不等于已重建每张图片的完整编码过程，也不能证明桌面端何时为该用户开启了某个开关。

## 去重为什么不只看图片外观

| 依据 | 能确认什么 | 不能确认什么 |
| --- | --- | --- |
| 原始字节 SHA-256 | 文件完全相同 | 同样画面换了编码，hash 可能不同 |
| 统一方向与 RGBA 后的完整像素摘要 | 尺寸及每个像素完全一致，可识别部分无损容器转换 | 不是模糊相似度，不能覆盖未知有损转换 |
| 已验证的版本关联 | 同一输入中校验过的附件与内嵌图，或管理员明确合并过的版本 | 不会仅因两张图看起来相似就自动合并 |

JPEG 转无损 PNG 可以保存完全相同的解码像素，但不能恢复 JPEG 编码前的细节。重复复制粘贴也不保证只出现两个 hash：剪贴板、客户端和编码路径都可能改变字节。已知版本可通过私有别名回到同一卡片；未知有损变换仍需视觉搜索和人工合并。

已经属于两张有效卡片的版本不能用 `--overwrite-images` 擅自合并。恢复原图时更新图片 hash 和 URL，同时保留原有日期、Prompt、标签、示例与点赞。导入计数和历史尺寸统计见[导入核查](2026-09-19-gallery-import-audit.md)。
